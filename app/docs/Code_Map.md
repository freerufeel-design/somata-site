# Somata — карта кода (модульная сборка 15.5)

Документ описывает, как устроен код после перестройки, где искать каждую часть и как проверять, что изменения не сломали геометрию. Замысел проекта (многоугольник как спираль нулевого порядка, три независимых выбора, инварианты) описан в [Somata_15_Project_Essence.md](Somata_15_Project_Essence.md).

## Загрузка

`index.html` подключает три скрипта:

1. `js/bootstrap/boot-guard.js` и `js/bootstrap/error-overlay.js` — обычные (не модульные) скрипты. Они должны работать, даже если граф модулей не загрузился, поэтому стоят отдельно.
2. `js/main.js` — единственная точка входа приложения (`type="module"`).

Модули браузер загружает только по `http(s)` и только с JavaScript-типом. Поэтому приложение запускается через `serve.py` (`start.bat`, `start.command`): это стандартный `http.server` Python с правильными MIME-типами и `Cache-Control: no-store`. Обычный `python -m http.server` на Windows берёт типы из реестра и часто отдаёт `.js` как `text/plain`; тогда, как и при открытии с диска, `index.html` показывает подсказку о запуске. Второй, собранной копии кода нет.

Каждый модуль явно импортирует то, что использует, и экспортирует то, что нужно другим. Общей глобальной области больше нет: раньше 2265 имён верхнего уровня из 138 скриптов были видны всем, теперь у каждого модуля свои.

### Порядок инициализации

В исходной версии многие скрипты при загрузке выполняли действия (вешали обработчики, создавали синглтоны, читали состояние, подготовленное предыдущими скриптами) и полагались на порядок `<script>` в `index.html`. Модули ES по умолчанию выполняются в порядке обхода графа импортов. При наивном переводе 131 модуль из 136 менял позицию, и 13 обращений к ещё не созданным константам падали бы.

Поэтому первой строкой каждого модуля стоит импорт предыдущего по историческому порядку:

```js
import './base-plan.js'; // initialisation order: this module runs after it
```

`js/main.js` импортирует последний модуль цепочки, и обход графа выполняет все модули ровно в том порядке, в котором раньше шли теги `<script>` (при распиле монолитов части встали на место исходного файла подряд). Циклические зависимости при этом безопасны: обращения вперёд по цепочке становятся обратными рёбрами.

Цепочка честно фиксирует текущую зависимость от порядка. Её можно убирать по частям: модуль, у которого при загрузке нет побочных эффектов и который импортирует только такие же модули, в цепочке не нужен. Сейчас под это условие подходят единицы, потому что почти всё зависит от `core/state.js`, а тот через `core/render-runtime.js` тянет интерфейс (см. «Что осталось»).

## Ошибки, которые раньше пропадали

653 пустых блока `catch` теперь вызывают `noteSuppressedError(место, ошибка)` из `js/core/suppressed-errors.js`. Поведение то же, но ошибки считаются по месту возникновения:

- `window.__somataSuppressedErrors()` — сводка;
- `?debugErrors` в адресе страницы или `localStorage.setItem('somata.debugSuppressedErrors', '1')` — вывод каждой ошибки в консоль.

На проверочных проектах в обычной работе ни один из этих блоков ничего не ловит.

## Оставшиеся глобальные API

Часть модулей по-прежнему обменивается объектами через `window.X = …` (например, `SomataMorphRegistry`, `SomataFeatureHost`, `SomataJumpTrace`, отладочные `window.__spiro…` и `window.__somata…`). Список из 181 имени лежит в `tools/window-apis.json`, ESLint разрешает читать их без импорта. Новый код лучше писать через импорт.

## Что осталось

- **Большие замыкания.** Шесть функций остались цельными, потому что внутри них общее приватное состояние: рендерер штрихов `gpu/stroke-renderer.js` (около 7,8 тысяч строк), `gpu/spiral-bezier-morph-renderer.js` (6,2 тысячи), `createMorphPlaybackModule` в `morph-runtime/blue/playback.js` (3,9 тысячи), `bindPresetRandomMorphControls` (3,2 тысячи), IIFE в `gpu/lamp-renderer.js` и `morph-runtime/manual-morph.js`. Их распил — ручное перепроектирование с проверкой скриншотами.
- **Связность слоёв.** Почти любой модуль транзитивно импортирует почти все остальные: замыкание импортов `geometry/orbit-builder.js` — около 160 модулей. Корень проблемы в том, что базовые модули (`core/state.js` → `core/render-runtime.js` → `ui/profile-presets.js`, `ui/floating-panels.js`; `core/palette.js` → интерфейс палитр) зависят от интерфейса. Следующий шаг — сделать `core/state.js` листом и вынести мелкие параметрические функции (`getRoundingStrength`, `getEffectiveLayerRadius`, `gcd`, признак пресэмплированного сплайна) в нижний слой. Тогда геометрия станет самостоятельным слоем, и цепочку порядка можно будет сокращать.
- **CSS.** `styles/app.css` отформатирован, но в нём около 1750 `!important` и 179 повторяющихся селекторов. Их нельзя слить автоматически без риска изменить каскад.
- **Мелочи.** ESLint показывает около 330 неиспользуемых переменных; 104 проверки `typeof` в сложных выражениях оставлены; DOM-идентификаторы `testMorph…` и имена `spiro…` не переименованы (на них завязаны CSS, разметка и формат файлов).

### Браузерные инструменты (`tools/`)

Headless Chrome не умеет показывать холст WebGPU, поэтому `tools/harness-inject.js` подменяет контекст холста текстурой и копирует её в 2D. Ещё он делает кадры детерминированными: виртуальные часы двигаются только по команде, `Math.random` с фиксированным зерном. На машине без GPU WebGPU работает через SwiftShader.

- `tools/geometry-golden.cjs` — 3354 вызова `buildOrbitPolylines` в браузере (сетка и все слои всех проектов `default.plist` на четырёх порядках), побитовый хеш; сравнение — `tools/geometry-compare.cjs`.
- `tools/visual.cjs` — скриншоты всех проектов `default.plist` в трёх моментах времени; сравнение — `tools/compare-visual.cjs`. Часть сцен недетерминирована и в исходной версии: GPU-конвейеры готовятся асинхронно в реальном времени, яркость ламп нарастает по числу кадров. Поэтому сравнивать надо с несколькими прогонами эталона, а при сомнениях увеличивать паузы (`BOOT_WAIT=8000 LOAD_WAIT=8000`, мс).
- `tools/refactor/split-module.cjs`, `move-module.cjs`, `outline.cjs` — инструменты, которыми резались монолиты: распил модуля по строкам с пересчётом импортов и цепочки, перенос модуля с исправлением всех путей, оглавление модуля.

19. **Спектральный режим проблеска: точный обруб по сектору и предсказуемое свечение** (вопрос). Короче: возможно, пока не сделано. Сейчас (`js/gpu/bezier-sweep-renderer.js`): граница сектора считается один раз на CPU как два вектора от оси, а пиксель проверяется векторными произведениями без atan2 — линия (ядро) обрезается точно по лучу. Но свечение классифицируется по ближайшей точке на отрезке кривой, поэтому оно обрывается не по лучу, а поперёк линии, и у границы заходит за неё на радиус свечения (хвост «конуса» на вашем скриншоте). Чтобы свечение обрывалось ровно по лучу, нужно проверять собственную позицию пикселя в координатах источника (обратное афинное преобразование), для копий Коридора — своё преобразование каждой копии. Предсказуемость яркости: свечение складывается через `max`, а не суммой, то есть соседние витки не накапливаются; настраиваемая угловая растушёвка края (резкий / мягкий на N°) сделала бы профиль управляемым. Нужно выбрать: резкий обруб по лучу или обруб с растушёвкой.
20. **Лампочки: на старте фазы одна всегда остаётся включённой** («в начале фазы лампочки в ключевой гаснут все сразу»). Причина: смена фазы меняет идентификаторы ламп — старые пропадают, новые рождаются тёмными (огибающая рождения), а перескок гасит лампу на старом месте; вместе это давало кадры совсем без света. Исправление (`js/render/lamp-stability.js`, «хранитель»): если в предыдущем кадре светила хотя бы одна лампа, а в этом свет упал ниже половины исходной яркости, то одна лампа остаётся полностью включённой — ближайшая к той, что светила последней; она не рождается заново и не перескакивает (встаёт сразу на своё место), остальные зажигаются плавно как обычно. Хранитель отпускается, когда остальные набрали яркость. Самое первое появление света (до этого ничего не светило) хранителя не включает. Побочный эффект: если на сцене единственная лампа и она перескакивает, она теперь не гаснет, а переставляется. Проверено тестами `tests/lamp-stability.test.cjs` (смена всех идентификаторов, общий перескок, ровно одна включена, ближайшая к последней; на записи Blue-морфинга тёмных кадров 0). Сам момент смены фазы на записи не воспроизводился (в записи один цикл), поэтому живая проверка — на вашей стороне.
21. **Заливка при смене числа вершин N в режиме Fade: старая гаснет, новая зажигается** («заливка должна резко погаснуть… пусть гаснет постепенно пропорционально фазе, подчиняясь „Смена режима“»). Причина: заливка берётся из общего контура кадра (`FrameContour`), и при Fade туда попадали сразу два замкнутых контура — старая и новая фигура. Они заливались одним веером с чётно-нечётным правилом и одной прозрачностью, поэтому в области пересечения заливка взаимно гасилась (центр оставался пустым), а яркость заливки сразу падала примерно до 43 % и держалась так до конца фазы. Исправление: каждый контур несёт своё «присутствие заливки» (`fillPresence`). Носители Fade (`js/morphs/types/fade.js`) помечают уходящую фигуру ролью −1, приходящую +1 и фазой; `morphPathFillPresence` (`js/geometry/morph.js`) считает присутствие как 1−u и u, где u = `profileModeTransitionProgress(фаза)`, то есть «Вся фаза / Начало фазы / Конец фазы» и «Часть фазы» действуют на заливку так же, как на смену профиля. Присутствие записывается в команду обводки (`js/render/gl-recording-context.js`, поле `fillPresence`), на пути Fade в `blue-fade` оно выставляется в `js/render/geometry-executor.js`, для ручного «тестового морфа» — в `js/morph-runtime/manual-morph.js` (Fade/Continuous/Light; у Light присутствие 0/1). `FillMeshPreparer.prepareFrameContour` (`js/render/fill-plan.js`) раскладывает контуры по группам с одинаковым присутствием (`mesh.fanGroups`: начало, длина в треугольниках, вес; группы с весом < 0,002 не рисуются), а `js/gpu/fill-mesh-renderer.js` рисует каждую группу отдельным проходом «трафарет + покрытие» со своей прозрачностью (альфа × вес). Кадры без присутствия (все остальные режимы) идут по-старому одним веером: `fanGroups = null`. Линия по-прежнему плывёт линейно по фазе — менялась только заливка. Замеры (безголовый Chrome, N 4→7, Fade, средняя яркость заливки по кадрам): было — скачок до ~43 % и плато, затем рывок в конце; стало — плавный рост 12,9 → 17,4 млн; «Начало фазы 30 %» — заливка полностью переходит за первые 30 % фазы, «Конец фазы 30 %» — держится старой до последней трети и затем переходит; circleSlide и topology без изменений. Тесты: `tests/fill-fade.test.mjs` (присутствие по «Вся/Начало/Конец фазы», группировка веера, отброс погасшей фигуры, возврат к одному вееру). Известное ограничение стенда: на программном GPU в безголовом Chrome изредка встречаются пустые кадры скриншота (в разных местах от запуска к запуску, и до правки тоже) — на живой видеокарте это не проверялось. Наложение двух заливок идёт обычным «source-over», поэтому в середине фазы на пересечении суммарная яркость чуть выше линейного среднего — так же складываются и сами линии.

23. **Заливка «на цикл вперёд»: предвыбор цели следующего цикла Blue-морфа.** («Нужно заранее, чтобы программа понимала. Раньше цель цикла выбиралась только в `prepareMorphCycle` на самой границе, поэтому заливка узнавала о ней в тот же кадр, когда фигура уже менялась. Теперь (`js/morph-runtime/blue/fill-lookahead.js`, чистый модуль) в конце `prepareMorphCycle` цикла N выбирается топология цикла N+1: N, K, число орбит (`customSuborbits`) и число копий орбит (`morphOrbitCopies`). Выбор делается теми же функциями и в том же порядке бросков: `chooseMorphTopologyTarget` вынесена из `buildMorphVisualTargets` (`targets.js`) без изменения поведения. Результат лежит в `runtimeState.morph.nextTopologyPlan` и на границе применяется, а не бросается заново (`buildMorphVisualTargets(layers, plan)`; число копий — в `prepareMorphCycle`). План принимается только если совпали слои (id), настройки выбора цели (подпись `planSignature`), номер цикла (`lampCycleSerial`) и слой действительно дошёл до той топологии, из которой план строился; иначе цель выбирается как раньше. План не строится: без «Моно-орбит» (`monoOrbitTransforms`), для спирали и хаос-звезды, при «Спираль: слои / порядок» в Морфе и при спиральных типах, фиксирующих N или K. Признак скачка (`fillWillJump`): моно-орбиты включены, контур замкнут, заливка в конце цикла видна и число орбит меняется (и вверх, и вниз: движок в обоих случаях дублирует совпадающие копии). При признаке прозрачность заливки умножается на множитель `fillLookaheadLevel` (в `applyFillMorphFrame`): последние 25 % цикла заливка гаснет по smoothstep до нуля, в начале следующего разгорается с того уровня, на котором остановилась (запоминается последний применённый, поэтому прерванный цикл не даёт скачка). Окно 25 % — константа `FILL_LOOKAHEAD_WINDOW`; «Смена режима» на это гашение не действует. Проверка в живом приложении (headless Chrome, N=6, K=2, моно-орбиты, заливка 70 %, 5 стыков подряд): N, K и число копий на каждом стыке совпали с планом; на стыке с признаком прозрачность заливки в хвосте 0,265 → 0,0003, а в начале следующего цикла 0,001 → полный уровень за 25 % фазы; на стыках без признака множитель ровно 1. Тесты `tests/fill-lookahead.test.mjs` (9): множитель, нет скачка на стыке, продолжение с остановленного уровня, признак скачка, план от конечной топологии цикла, условия отказа и принятия плана. **Не сделано / ограничения:** (а) при частичном покрытии параметров по слоям (`geometry.N`, `geometry.K`) цель слоя перезаписывается уже после выбора, и признак для такого слоя может не совпасть с фактом; (б) сам скачок заливки при росте числа орбит на безголовом стенде не воспроизводился, поэтому проверка только по значениям, картинки «до/после» нет; (в) лампы заранее не готовятся (тот же план годится и для них); (г) уточнение к пункту 22(а): по замеру проекта 5 статика ставит у каждой вершины группу из 3 ламп (17 групп в пределах 25 px, радиус 191–194 px у слоя «Внешний каркас»), а морф — по одной. Логические узлы профиля в морфе лежат в сетке из 32 парных узлов (флаги `lampLogicalCornerFlags`: 8 у источника, 10 у цели), а путь, по которому морф ставит лампы, взят по 9 точек на ребро, поэтому прямого соответствия «узел профиля → точка пути» нет. Нужна привязка по доле дуги и проверка на всех типах морфа (circleSlide, topology, calm, topoCircle) — не сделано. **Обновление (пункт 25):** гашение всей заливки и признак «скачка» удалены; вместо них меняется только область внутри «лишних» контуров. 25. **Заливка в «Математическом»: центр пустеет или заливается заранее, а не скачком на стыке; меняется только эта область.** («Режим математический может оставить центр пустым», «если знаешь, что в начале следующей фазы заливка из центра исчезнет, она должна исчезнуть оттуда заранее», «скачки по скруглению».) Исправление: (1) план соответствия (`polygonCorrespondence`, `js/geometry/morph-math.js`) отмечает у пути `sourcePathPresent` / `targetPathPresent`, общий помощник `polygon` (`skeleton-runtime.js`) передаёт это носителю, `orbit-builder.js` — пути (`_fillPathSource/_fillPathTarget`), `drawPreparedMorphGeometry` (`morph.js`) ставит на команду вес лишнего контура `fillGhost` = {g, dir} (`fillGhostWeight` в `fill-lookahead.js`): при слиянии g уходит в 0 за последние 25 % фазы, при разделении поднимается от 0 за первые 25 %; (2) `fill-plan.js` раскладывает веер как «уходящие | обычные | приходящие» (`ghostFillLayout`) и строит до четырёх перекрывающихся групп, каждая — своя чётно-нечётная заливка с прозрачностью 1−(1−α)^p (`fill-mesh-renderer.js`, параметр `power`). Где группы совпадают (вне лишних контуров), их доли складываются ровно в α, поэтому меняется только область внутри лишнего контура, например центр; (3) «заранее» для разделения: топология следующей фазы выбирается заранее (план из пункта 23), и орбиты цели, которые в следующей фазе раздвоятся, получают в хвосте текущей фазы дубли в заливке (`__fillSplitAhead`, `fillSplitAheadWeight`). 28. **Лампы вершин в морфе идут по своим траекториям, без сопоставления «к ближайшей».** («В некоторые вершины не приходят лампочки, там они просто загораются, а в другие приходит больше, чем надо. У каждой точки есть начальное и конечное место… Меня не интересует сведение к ближайшей доступной точке».) Раньше в circleSlide лампы вершин считались отдельно от геометрии (`collectTrueLinearKeyLampPoints`): каждая лампа сопоставлялась с вершиной источника и цели по ближайшему углу (`markMappedAnglePopulation`), а её место на контуре задавала доля «номер вершины / число вершин», перетекавшая от i/n к j/m. Отсюда вершины без пришедшей лампы, где она загоралась на месте, и вершины с двумя лампами.
