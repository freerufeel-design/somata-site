# Somata 16.2 GPU Fourier — этап 1

База: 16.1 Skeleton First. Формат проекта, скелет, формулы порядка, исходная окружность, фазы морфинга и меню направляющих не перестраивались.

## Реальный маршрут

`Skeleton → Order → Profile source → CPU resampling (96) + reference → GPU DFT / weights / inverse (288) / endpoints / radius → indexed stroke → WebGPU composition`.

`geometry/fourier.js` содержит общий CPU/GPU алгоритм подготовки входа и исходный CPU-эталон. `gpu/fourier-compute.js` — вычислительный WGSL (64 потока на независимую ветвь). `render/gl-recording-context.js` и `render/stroke-command-cache.js` записывают приватные дескрипторы вместо вымышленных координат. В `gpu/stroke-renderer.js` вычисления записываются до отрисовки в одном командном буфере; вершины хранятся в storage buffer. Программа не читает его обратно на CPU. Для переменной толщины передаётся поле widthScale. Топология индексов и стили пока формируются на CPU. Убран неиспользуемый eager Path2D для режима Фурье (его оба потребителя уже обходили).

## Область применения

Экспериментальный маршрут автоматически пробуется при готовом compute pipeline, активном Фурье, скруглении 10–200%, линии без дополнительных потребителей контура, скруглённых стыках и отсутствии Коридора. Включены статический маршрут и попытка для нескольких основных Blue/manual-провайдеров; если провайдер уже выдал отфильтрованный CPU-контур, используется CPU-совместимость. Результат попытки не выдаётся за миграцию всех типов морфинга. Отдельные ветви спиралей поддержаны при отсутствии альфа-градиента Коридора.

При скруглении 0–<10% сохраняется точный CPU-алгоритм добавления исходных узлов; при включении заливки, Glow, Outline, ламп, Web, Граффити, других потребителей, Коридора, вырожденных ветвях, несовместимой записи, прогреве/ошибке компиляции используется прежний маршрут. Нельзя выдавать GPU-дескриптор в общую CPU-геометрию. Orange/Green/Lightning и GPU-дуговые таблицы не мигрировали. Полное GPU-resampling, GPU-арки, GPU-эффекты, переиспользование новых буферов и перенос Коридора — отдельные этапы. На этом этапе создаются буферы для каждого GPU batch; выигрыш FPS не измерен.

## Диагностика

В DevTools Console после включения Фурье на слое без эффектов:

```js
__somataGpuFourierStatus()
```

`lastDecision.reason === 'resident-compute'` означает, что сформирован вычислительный и рисующий командный буфер; `computeBatches` и `railsEncoded` — счётчики **закодированных** команд, а не доказательство успешного GPU-исполнения. `pipelineReady`, `lastError`, `fallbackBatches` помогают понять отказ. Для сравнения с предыдущим CPU-расчётом: `window.__somataGpuFourierEnabled = false`, затем изменить параметр для обновления кадра. Вернуть GPU: `window.__somataGpuFourierEnabled = true` (настройка только текущей страницы).

Независимая диагностика WGSL на реальном устройстве: при работающем сервере открыть `http://localhost:8000/app/tools/gpu-fourier-check.html` (или эквивалентный адрес хостинга) и нажать «Запустить проверку». Она сравнивает storage buffer со сохранёнными CPU-эталонами 14 открытых/замкнутых кривых, включая ширину, трансформацию и нормализацию. Только диагностическая страница использует readback. Допуск 0.05 координатной единицы и 0.0001 по widthScale. Эталон обновляется командой `node tools/generate-gpu-fourier-fixture.mjs` из app.

## Проверено в среде разработки

122 исходных теста и 5 новых Node-тестов проходят. Новые проверки сравнивают независимую JS-транскрипцию математики шейдера с CPU-эталоном, проверяют упаковку данных, приватную запись, mock GPU-encoding и границы применения. Node-тесты не компилируют и не исполняют WGSL. Локальная навигация Chromium блокируется политикой среды (`ERR_BLOCKED_BY_ADMINISTRATOR`), поэтому реальный GPU-тест, визуальный прогон и замеры производительности не выполнены. Диагностическая страница поставляется для проверки на пользовательском устройстве.
