# Somata 7.11.0 — как устроено приложение

Этот файл описывает **текущую архитектуру Somata человеческим языком**. Он нужен не как история версий, а как карта проекта: где живут данные, как строится один кадр, кто отвечает за Morph, Spiral, Web, Lightning и остальные эффекты, как они попадают в GPU и какие правила нельзя нарушать при следующих правках.

Если коротко, главный принцип такой:

> **Сначала определяется одна актуальная геометрия слоя на этот кадр. Затем все эффекты смотрят на эту же геометрию и рисуют свои части в общем порядке. Статика и динамика не должны иметь две разные художественные реализации одного эффекта.**

Исключения допустимы только там, где сама геометрия требует другого технического carrier'а — прежде всего у строгой Spiral, которая сохраняет собственный retained Bézier/GPU путь. Но даже в этом случае смысл эффекта, его параметры и порядок композиции остаются общими.

---

## 1. Что такое Somata с точки зрения архитектуры

Somata состоит из пяти больших частей:

1. **Состояние проекта** — слои, параметры, палитры, Morph, Corridor, эффекты.
2. **Геометрия кадра** — ответ на вопрос «какая именно фигура существует прямо сейчас».
3. **Планы эффектов** — ответ на вопрос «что именно надо нарисовать поверх этой геометрии».
4. **GPU-композиция** — фактическая сборка Web, Fill, Glow, Base, Lamps, Lightning и других проходов в изображение.
5. **Scheduler** — единый ритм, который запускает анимации и просит следующий кадр.

UI только меняет состояние. UI **не должен сам рисовать эффект** и не должен иметь собственную версию геометрии.

---

## 2. Два вида состояния слоя: authored и frame

Это один из самых важных моментов.

### Authored layer

`state.layers` — это то, что сохранено в проекте и что редактирует пользователь.

Там живут, например:

- N/K и параметры профиля;
- Spiral;
- Fill/Line/Glow;
- Web;
- Lamps;
- Sweep/Lightning;
- Particles;
- параметры Corridor;
- цвета, прозрачности и т. д.

Это **долгоживущие данные проекта**.

### Frame layer

Во время Morph или другого преобразования на экране может находиться геометрия, которая уже не равна исходному authored layer. Поэтому renderer работает через `frameCtx`.

Главные поля:

- `frameCtx.layer` — геометрическое представление слоя **на текущий кадр**;
- `frameCtx.effectLayer` — постоянный authored-слой, откуда берутся живые настройки эффектов;
- `frameCtx.geometryPlan` — какой тип геометрии выбран и динамический ли он;
- `frameCtx.effectsPlan` — подготовленные настройки активных эффектов;
- `frameCtx.frameId` — номер кадра;
- `frameCtx.frame` — общая информация обо всём кадре.

Зачем это разделение: Morph имеет право временно менять форму, но не должен портить настройки проекта или заставлять эффекты читать случайную промежуточную копию параметров.

### 2.1. FrameContour — одна форма слоя на один кадр

Для обычной геометрии в 7.8.3 главный объект формы кадра — `FrameContour`.

Файл: `js/geometry/frame-contour.js`.

Его задача очень простая: **один раз за кадр зафиксировать именно тот контур, которым реально рисуется Line, и больше не позволять эффектам заново угадывать форму**.

Схема такая:

```text
Morph / Static geometry
        ↓
видимые Line stroke commands текущего кадра
        ↓
один FrameContour
        ↓
 ┌────────┬────────┬──────────┬───────────┬────────────┐
 Line     Fill     Web        Graffiti    Sweep/Lightning
```

`FrameContour` хранит **две проекции одной и той же формы**, а не две независимо рассчитанные формы:

- `commands` — фактические screen-space stroke commands, которыми обязана рисоваться обычная Line;
- `screenPaths` — связанная топология этих же команд для Fill;
- `paths` — эти же `screenPaths`, переведённые обратно в локальные координаты слоя для Web/Graffiti/Lightning.

Важное отличие 7.8.3: `screenPaths` собирается **через границы stroke-команд**. Если четыре стороны многоугольника были записаны четырьмя отдельными `stroke()` и конец одной стороны точно совпадает с началом следующей, это всё равно один замкнутый `FrameContour`. Несвязанные концы никогда не соединяются «по близости».

После того как обычный слой создал `FrameContour`, native topology/green Base не имеет права рисовать Line по второму carrier'у. Видимая Line обязана использовать `FrameContour.commands`. Иначе формально общий контур существовал бы для эффектов, но сама синяя линия всё равно могла бы находиться в другом месте — именно этот скрытый обход был причиной расхождений в 7.7.9.

`FrameContour` существует и когда Line визуально выключена. На время записи carrier'а visibility/profile-флаги временно открывают только геометрическую запись, затем возвращаются обратно. Поэтому независимые Fill и Web не теряют форму при выключении Line.

Главное правило:

> **Обычный эффект не имеет права заново строить базовый контур из authored layer, Morph pair, rounded polyline или собственного sampling. Он получает `FrameContour` и меняет только свой визуальный способ рисования поверх него.**

Это не запрещает Lightning добавлять разряды, Web строить нити, а Graffiti — ribbon. Запрещено только заново определять, где находится сама базовая линия.

`FrameContour` кешируется на `frameCtx`: первый потребитель строит его, остальные получают тот же объект. Это одновременно устраняет расхождение геометрии и повторную CPU-работу.

Жёсткий контракт 7.8.3:

```text
один frame/layer
      ↓
FrameContour.commands ─────────────→ Line
      │
      ├─ FrameContour.screenPaths ─→ Fill
      │
      └─ FrameContour.paths ───────→ Web / Graffiti / Lightning
```

Для ordinary geometry после создания `FrameContour` запрещён fallback на «другую, но похожую» форму. Если shared contour временно нельзя подготовить, правильнее пропустить конкретный pass и диагностировать ошибку, чем показать Fill/Web по неверной границе.

Это также правило производительности: длины/стыки/топология базовой формы считаются один раз. Эффект может строить свои нити, ribbon или jitter, но не должен повторно проходить authored/Morph geometry ради восстановления той же границы.

Запись Line-carrier обязана быть полностью самодостаточной по стилю. Recorder получает `strokeStyle`, `lineWidth`, `lineCap`, `lineJoin`, `miterLimit` и alpha из `frameCtx`, а не наследует текущее состояние `mainCtx`. Иначе эффект, который запросил `FrameContour` до Base-pass, может случайно записать Line цветом предыдущего Canvas-состояния (типичный симптом — линия внезапно становится чёрной).

Есть два осознанных исключения:

- **strict Spiral** — её authoritative carrier остаётся retained GPU/Bézier rail поздней 7.7.9;
- **Corridor** — использует master contour и трансформированные copies, потому что это не новая базовая форма, а многократное размещение одной формы.

Исключения не дают эффектам право иметь собственный художественный контур. Они только меняют технический carrier общей геометрии.

## 3. Главный инвариант: статика и динамика

Правило Somata:

> **Эффект не должен иметь отдельную “статическую картинку” и отдельную “морфовую картинку”.**

Правильная схема:

```text
текущая геометрия кадра
        ↓
единый подготовщик эффекта
        ↓
единый renderer эффекта
```

В статике «текущая геометрия кадра» просто совпадает с authored geometry.

Во время Morph она является промежуточным состоянием Morph.

После этого Web, Lightning, Graffiti, Lamps и остальные эффекты должны получать геометрию через свои обычные контракты, а не выбирать художественно другую реализацию только потому, что `Morph active === true`.

### Что считается ошибкой архитектуры

Плохо:

```text
if static → drawLightningStatic()
if morph  → drawLightningMorphCompletelyDifferently()
```

Хорошо:

```text
currentCarrier = resolveCurrentGeometry()
lightningData = prepareLightning(currentCarrier)
drawLightning(lightningData)
```

### Текущий контракт Lightning

Для обычной, не strict-Spiral геометрии:

```text
static ─┐
        ├→ prepareLayerFrameSweepData() → SweepGPURenderer
Morph ──┘
```

То есть обычная Lightning в статике и Morph использует один prepared-path обработчик.

Для **strict Spiral** остаётся специальный retained GPU Arc carrier. Это не вторая художественная молния, а технический способ не разрушать точную Spiral-геометрию CPU-материализацией.

## 4. Как рождается один кадр

Упрощённая цепочка выглядит так:

```text
Scheduler
   ↓
renderMainCanvas()
   ↓
для каждого слоя:
   prepareMainLayerFrame()
   ↓
   выбрать актуальную геометрию
   ↓
   построить RenderGraph / Consumer Demand
   ↓
   подготовить только нужные данные
   ↓
   подготовить effectsPlan
   ↓
   запечатать render snapshot
   ↓
   выполнить render passes
   ↓
собрать Layer Scene / Frame Scene
   ↓
финальная композиция на main canvas
```

### Почему сначала планирование, потом рисование

Во время подготовки renderer выясняет, что реально нужно этому слою.

Например:

- если Web выключен — не надо строить его нити;
- если никто не требует CPU path — не надо материализовывать CPU path;
- если strict Spiral может остаться полностью на GPU — нельзя вытаскивать её через упрощённую CPU-геометрию;
- если нужен Exact Arc — GPU scheduler должен подготовить Arc до эффекта, который его читает.

Это позволяет не строить всё подряд на каждом кадре.

## 5. Scheduler — один хозяин времени

Файл: `js/core/scheduler.js`.

У приложения есть **общий scheduler**, а не отдельный `requestAnimationFrame` на каждый эффект.

В scheduler регистрируются задачи вроде:

- Morph;
- Sweep/Lightning;
- другие непрерывные анимации;
- запрос основного repaint.

Главный смысл: один эффект не должен запускать бесконтрольный второй render loop параллельно основному.

### Watchdog Morph

Scheduler следит не только за логикой Morph, но и за фактическими задержками кадра.

Он умеет различать, например:

- долгий animation task;
- долгий `renderMainCanvas`;
- длинную main-thread task;
- большой разрыв между `requestAnimationFrame`.

Поэтому сообщение `[Somata Morph Freeze]` не обязательно означает, что сломана математика Morph. Очень часто оно означает, что Morph просто оказался активен в тот момент, когда render/GPU/driver занял сотни миллисекунд.

### Важное правило времени: линия и эффекты не должны расходиться

У Base/Line, Morph и временных эффектов должен быть один смысл времени: **время текущего кадра**.

Если браузер или GPU задержал кадр на 200–500 мс, следующий кадр может визуально перескочить вперёд. Это неприятно, но правильно: вся сцена снова оказывается в одной временной точке. Нельзя отдельно «смягчать» задержку только для Morph, сдвигая его `cycleStart`, пока Web/Graffiti/Sweep/Lamps продолжают считать время от `performance.now()`. Тогда получается худший вариант: линия выглядит замершей, а эффекты продолжают двигаться поверх неё.

Поэтому в текущей 7.8.3 (начиная с поздней 7.7.9) после исправления line/effect sync **нет Morph-only stall compensation**. Длинные кадры по-прежнему диагностируются watchdog'ом, но геометрическая линия на следующем кадре догоняет общую wall-clock timeline. Если нужна будущая визуальная стабилизация после stalls, она должна вводиться только как единый visual clock для всей сцены, а не как локальная поправка одного Morph.

## 6. Morph: один смысл, разные carriers

Основной контроллер: `js/core/morph-controller.js`.

Текущая архитектура Morph отделяет два понятия:

1. **Morph semantics** — *что* сейчас происходит с профилем/формой.
2. **Carrier mapping** — *как* эта форма физически представлена для конкретного типа геометрии.

То есть Morph mode не должен переписываться только потому, что слой является Spiral.

### Blue / Orange / Green

У приложения есть несколько систем изменения состояния:

- Blue Morph — основной геометрический Morph;
- Orange — отдельная генерация/переходы собственного семейства;
- Green / Project Morph — переход между проектными состояниями.

`SpiroMorphController` определяет, кто сейчас владеет отображаемым кадром.

### Важное правило

`gpuWarming` — это подготовка GPU-ресурсов, а не пауза Morph.

Прогресс Morph не должен обнуляться или ждать только потому, что специализированный renderer ещё прогревается.

## 7. Polygon и профиль

Для обычного polygon профиль является общей смысловой основой.

Без rounding стыки сегментов должны оставаться острыми. Сегменты являются Bézier-сегментами между ключевыми точками. Rounding не должен превращаться в отдельный альтернативный polygon renderer — он модифицирует локальные угловые участки геометрии.

Ключевой принцип:

> **Morph двигает carrier/ключевые точки. Построение видимого профиля должно оставаться тем же по смыслу, что и в статике.**

Это и есть причина, по которой boundary `t=0` должен совпадать со статическим кадром, а не внезапно переходить на другую аппроксимацию.

## 8. Spiral — особый carrier, но не отдельный мир

Spiral является первой классной геометрией, а не эффектом поверх polygon.

Основные файлы:

- `js/render/spiral-geometry-policy.js`
- `js/render/spiral-role-adapter.js`
- `js/gpu/spiral-bezier-morph-renderer.js`

### Главное правило Spiral

Поздняя 7.7.9 использует **retained Bézier rail**. Его нельзя без причины заменять старой общей CPU-аппроксимацией.

Spiral transport и global Morph mode — разные вещи.

Например, `phaseCircle` у Spiral описывает транспорт carrier'а. Он **не означает**, что глобальный `topology` Morph надо переписать в старый Circle rebuild.

### Режимы Spiral transport

На уровне архитектуры они означают примерно следующее:

- `continuous` — непрерывный транспорт с фиксированными N/K;
- `phase` — N фиксирован, K двигается как фазовый шаг;
- `phaseCircle` — phase + clone/merge ветвей без отдельного fade;
- `minimalTurn` — сохраняется шаг, N меняется через clone/merge с минимальным поворотом;
- `topology` — ключевые точки перемещаются Cartesian способом;
- `torn` — точное Bézier subdivision без arc-resampling.

### Strict Spiral

Когда кадр признан strict Spiral, renderer старается не выходить из точного retained GPU carrier.

В этом режиме опасно:

- строить “похожий” CPU path ради эффекта;
- отправлять эффект на Canvas fallback;
- материализовать промежуточную Layer Scene способом, который ломает GPU-only цепочку.

Если специализированный pass не может отработать, правильнее пропустить именно этот pass и записать диагностическую ошибку, чем тихо заменить геометрию другой.

## 9. RenderGraph: кто заранее говорит, что ему нужно

Файл: `js/render/render-graph.js`.

Центральный renderer не должен знать внутренности каждого эффекта.

RenderGraph работает как список требований.

Базовое ядро знает только Base/Fill. Остальные features сами объявляют, что им нужно, например:

- positions;
- segment topology;
- approximate Arc;
- exact Arc;
- CPU path;
- Canvas vector;
- Fill;
- Lamps;
- lamp identity.

Дальше `consumer-demand.js` превращает эти требования в конкретный список данных, которые надо подготовить.

### Зачем это нужно

Если добавить новый эффект, нормальный путь — зарегистрировать его capability/demand, а не вставить очередной `if (newEffect)` в `main-pipeline.js`.

---

## 10. FeatureHost — firewall между эффектами

Файл: `js/render/feature-host.js`.

Каждый эффект считается **гостем renderer'а**.

Он должен заранее объявить:

- какие планы он читает;
- какие чужие outputs ему разрешено читать;
- какие outputs он имеет право менять.

Во время pass'а feature получает изолированный `frameCtx`-view.

Если эффект пишет поле, которое ему не принадлежит, эта запись не должна молча протечь в соседний эффект.

Если pass падает, его неподтверждённые изменения не коммитятся.

### Зачем это было введено

Без этого Web мог случайно зависеть от scratch-поля Graffiti, Lightning — от внутреннего результата Base, а следующий рефакторинг одного эффекта ломал совершенно другой.

## 11. Pass Registry — центральный pipeline не знает названия всех реализаций

Файл: `js/render/pass-registry.js`.

`main-pipeline.js` отвечает за **порядок стадий**, но реализация эффекта живёт в своём модуле.

Стадии:

```text
UNDERLAY
FILL
OVER_FILL
GLOW
BASE
POST_BASE
```

Стадии задают **dependency-safe порядок подготовки/вызова pass'ов**, но начиная с bugfix 7.8.3 они больше не являются вторым независимым источником художественного compositor-order. Фактический bottom→top порядок GPU-команд задаёт один `SomataEffectStackOrder`.

Технические позиции pass'ов остаются:

```text
Fill                 → FILL
Web                  → OVER_FILL
Glow                 → GLOW
Base / Line          → BASE
Profile / Graffiti   → POST_BASE
Lamps                → POST_BASE
Sweep / Lightning   → POST_BASE
Sprite / Particles   → POST_BASE
```

По умолчанию художественный стек снизу вверх такой:

```text
Fill
→ Web
→ Geometry (Glow / Base / Line / Profile / Graffiti)
→ Lamps
→ Sweep / Glint / Lightning
→ Motion / Sprite
→ Particles
```

Пользователь может менять порядок этих семантических групп в **File → Настройки → Порядок эффектов** перетаскиванием строк. Один и тот же порядок используется для Static и Morph и одновременно определяет phase deferred GPU Layer Scene commands. Внутренний sub-order компонентов группы `Geometry` остаётся техническим инвариантом и отдельно не перетаскивается.

Дефолт по-прежнему гарантирует **Fill ниже Web**, поэтому штатная паутина видна одновременно с заливкой. Если пользователь сознательно переставляет Web и Fill, compositor обязан физически выполнить выбранный порядок, а не порядок подготовки pass'ов.

Часть проходов может физически объединяться в один GPU batch, но их итоговый художественный порядок должен соответствовать `SomataEffectStackOrder`.

### Fast-path художественного стека

`SomataEffectStackOrder` **не означает**, что для каждого слоя на каждом кадре нужно обязательно открывать отдельную offscreen `Layer Scene`. Перед render-pass'ами строится лёгкий effect-order plan по фактически активным группам. Если заводской/текущий порядок можно сохранить существующим совместным GPU batch'ем, renderer обязан использовать более дешёвый путь.

В частности, для ordinary geometry при выключенной Web и Fill непосредственно под Geometry заливка снова может входить в общий Line/Glow stroke batch. Отдельная ordered Fill-команда нужна только когда Web активна или пользовательская перестановка действительно отделяет Fill от Geometry. Аналогично neutral Layer Scene root открывается заранее только если поздний технический pass художественно переставлен ниже Geometry и ни Fill, ни Web не могут сами безопасно стать первым compositor command.

Важно: такое объединение является только **внутренним fast-path**, а не объединением художественных слоёв. `Fill` и `Geometry` остаются разными группами `SomataEffectStackOrder`. Если активная группа (в частности Web) стоит между ними, `standaloneFill` становится жёстким контрактом всего кадра: stroke batch Geometry не имеет права повторно прикрепить Fill даже при отсутствии/потере transient-флагов предыдущего Fill-pass. Если ordered Fill временно не готов, он пропускается с repaint, но не дорисовывается поздно уже внутри/поверх Geometry. Поэтому порядок `Fill → Web → Geometry` физически означает три независимые compositor-позиции.

Это правило производительности: **меню порядка задаёт семантику композиции, но не должно само по себе переводить весь renderer в дорогой универсальный offscreen path**. Static и Morph используют один и тот же planner. `frameCtx` переиспользуется, поэтому effect-order plan нельзя читать как transient cache прошлого кадра без проверки generation; текущая реализация пересчитывает его из live snapshot там, где от него зависит admission Fill/Spiral.

## 12. Layer Scene — общий прозрачный холст слоя на GPU

Файл: `js/render/layer-scene-service.js`.

`Layer Scene` можно представить как прозрачную GPU-текстуру, в которую по очереди добавляются части одного слоя до финального вывода.

Очень важно: **эффекты не имеют права самостоятельно открывать и управлять низкоуровневой Layer Scene**.

Они обращаются к `SomataLayerSceneService`.

Сервис умеет:

- найти уже открытую resident scene;
- открыть её;
- дать target;
- поставить command buffer в очередь с нужной phase;
- отметить, что scene deferred/presented;
- безопасно материализовать её, когда это разрешено.

### Зачем единый сервис

Иначе получалась ситуация:

```text
Web открыл одну scene
Base открыл вторую
Lightning решил, что scene уже готова
потом один pass затёр прозрачностью результат другого
```

Именно поэтому владение scene централизовано.

## 16. Fill

Основные файлы:

- `js/render/fill-plan.js`
- `js/render/fill-pass.js`
- `js/render/fill-geometry-adapter.js`
- `js/render/spiral-fill-adapter.js`

Base не выбирает Fill backend.

### Главное правило Fill

Для обычной, не Spiral-геометрии у Line и Fill **нет двух разных контуров**.

Authoritative source — `FrameContour` текущего кадра. `fill-geometry-adapter.js` **не читает raw stroke commands заново** и не сшивает свою копию контура. Он получает уже готовый `FrameContour`, а `FillMeshPreparer.prepareFrameContour()` строит stencil mesh только из `FrameContour.screenPaths`.

Поэтому Static и обычный Morph отличаются временем жизни carrier, но не алгоритмом формы Fill:

`current geometry -> FrameContour once -> screenPaths -> native GPU stencil Fill`

Особый случай — острый профиль без скругления. Такая фигура может быть записана несколькими отдельными открытыми Bézier-сегментами и даже несколькими отдельными stroke commands. Их соединяет сам `FrameContour`: только конец-в-конец с точным малым допуском. Fill уже получает итоговую замкнутую `screenPath` и ничего дополнительно не реконструирует.

Это правило нужно для острого сочленения: если Line состоит из Bézier-сегментов с вершинами на окружности, Fill обязан иметь ровно ту же границу, а не заново вычисленную аппроксимацию многоугольника.

Отдельные retained-пути остаются только там, где сама Line не материализуется в обычные stroke commands:

- поздняя Spiral 7.7.9 использует свой Spiral Fill adapter;
- Corridor использует свой master/copy carrier;
- эти пути нельзя заменять старым `circle rebuild` ради унификации.

Fill сам решает:

- можно ли в текущем effect-order plan **сохранить Fill внутри общего Geometry batch** вместо открытия отдельной Layer Scene;
- можно ли использовать native GPU fill;
- какой geometry carrier является authoritative;
- нужен ли prepared mesh;
- можно ли встроить Fill в Layer Scene;
- был ли Fill реально committed.

Критерий правильности здесь простой: если убрать цвет и оставить только границу Fill, она должна совпадать с геометрией Line текущего кадра. Изменение Morph, rounding или профиля не должно создавать второй независимый контур Fill.

### Типы Fill

В UI один список содержит четыре художественных варианта:

- **Плотный** — обычная Fill с `fillRule = nonzero`;
- **Математический** — обычная Fill с `fillRule = evenodd`;
- **С накоплением** — current-frame Fill добавляется в отдельную persistent history texture слоя; история очищается циклически по `fillAccumulationSeconds`;
- **Затухающая — резкая** (`fillType = fade`) — сохранённый исходный layered/iso эффект. Current-frame Fill проходит отдельный GPU post-process без истории; редкие бинарные кольца выборок намеренно оставляют выраженные контурные слои. Старые проекты с `fillType = fade` продолжают выглядеть так же.
- **Затухающая — плавная** (`fillType = fadeSmooth`) — та же current-frame Fill и те же `fromCenter/toCenter` + `fillFadeHardness`, но глубина оценивается непрерывно по нескольким концентрическим кольцам linear-alpha выборок. Полученное поле проходит `smoothstep`, поэтому переход следует контуру фигуры, но без выраженных ступеней. Плавный режим не имеет history texture и не должен менять sharp-ветку.
- **Контракт Жёсткости fade** — и sharp, и smooth сначала строят поле глубины, которое **не зависит от `fillFadeHardness`**. Ползунок только двигает монотонный порог по этому полю: `0%` всегда пусто, `100%` всегда обычная Fill, а при движении 0→100 ни один пиксель не имеет права уменьшать свою coverage. `fromCenter/toCenter` меняет направление роста области, но не направление самого ползунка.

Важно: UI объединён, но внутренние контракты **не смешиваются**. `fillRule` отвечает за topology обычной маски, а `fillType = normal | accumulation | fade | fadeSmooth` — за способ композиции результата. Старые проекты без `fillType` мигрируют в `normal`.

`accumulation` и `fade` всегда получают отдельную Fill-команду и не могут быть слиты обратно в Geometry batch. `normal` сохраняет прежний fast-path, когда effect-order это позволяет. Это необходимо, чтобы специальные режимы не меняли поведение стабильных Плотной/Математической заливок.

Обычная ordered Fill обязана сначала строиться в чистой current-frame texture. Нельзя использовать persistent MSAA scratch с `loadOp: load`: это снова превратит обычную полупрозрачную Fill в случайное накопление между кадрами. История разрешена только внутри явного `fillType = accumulation`.

Специализированный Fill pipeline также не имеет права определять жизнеспособность базовой Fill. В частности, shader/pipeline `fade` и будущие специальные типы инициализируются изолированно: ошибка validation специального WGSL диагностируется только для этого режима и **не переводит общий native Fill renderer в `ready = false`**. `Плотный` и `Математический` должны продолжать работать даже если дополнительный Fill shader недоступен.

### Fill и Line включаются независимо

`lineVisible` управляет только видимостью основной линии. Он **не входит** в условие существования Fill. Поэтому можно скрыть Line и оставить ту же заливку на том же `FrameContour`. Это важно и для Static, и для Morph: скрытие линии не должно разрушать геометрию, которая нужна Fill/Web/Graffiti/Lightning.

UI-контракт такой:

- ПКМ по кнопке палитры `🎨` — глобально выключить/включить Fill;
- в статике запоминается точный набор слоёв, у которых Fill был включён, и восстанавливается именно он;
- во время активного Morph выключение ставит `fillLayersMin = 0` и `fillLayersMax = 0`;
- повторное включение восстанавливает последнее вручную заданное число/диапазон слоёв, но минимум становится не меньше `1`;
- если пользователь вручную поставил, например, `3–3`, это значение сохраняется как память переключателя;
- ПКМ по `Геометрия`/звезде переключает только Line. Fill от этого не меняется;
- `Shift+ПКМ` по палитре оставлен для быстрого меню палитр, потому что обычный ПКМ теперь принадлежит Fill.

Есть важная техническая деталь: `frameCtx` переиспользуется между кадрами. Поэтому ссылка на `_glStrokeCommands` сама по себе **не означает**, что команды относятся к текущему кадру. Fill может выполняться раньше Base и увидеть массив от прошлого кадра. Использовать carrier разрешено только когда `_glStrokeCommandFrameId === frameCtx.frameId` и совпадает вариант carrier; иначе текущие stroke commands должны быть построены заново через общий provider. При начале нового frame context эти transient-поля очищаются. Иначе визуально получается характерный симптом: Line уже находится в новой фазе Morph, а Fill остаётся на старой форме и выглядит как отстающая/вылезающая из-под линии заливка.

## 17. Web / Паутина

Основные файлы:

- `js/render/web-plan.js`
- `js/render/web-pass.js`
- `js/render/web-morph-bridge.js`
- `js/gpu/web-thread-scene-renderer.js`
- `js/gpu/web-morph-renderer.js`

Web технически подготавливается на стадии `OVER_FILL`, но его **физическая compositor-позиция** берётся из `SomataEffectStackOrder`. В заводском порядке Web расположен выше Fill и ниже группы Geometry; пользователь может переставить эти группы в File → Настройки.

Fill/Web могут оказаться первыми GPU-проходами слоя, поэтому `SomataLayerSceneService` сам отвечает за warm-up `WebGPUStrokeRenderer` перед проверкой/открытием external Layer Scene. Web не должен зависеть от того, успел ли более поздний Base/Line batch случайно инициализировать renderer. Иначе получается bootstrap deadlock: Web ждёт Layer Scene, а Layer Scene ждёт Line-pass, который идёт позже.

Для **ordinary Polygon/обычного Morph** готовая Web-геометрия не имеет права исчезать только из-за временной недоступности WebGPU Layer Scene или `WebGPUWebThreadSceneRenderer`. В этом случае 7.8.3 использует восстановленную лестницу презентации из стабильной 7.3.20: сначала текущий GPU/WebGL backend, затем Canvas fallback. Важно: fallback **не строит другую форму** — он рисует те же thread commands, подготовленные из текущего `FrameContour`. Поэтому это резервный backend, а не резервная геометрия.

Для **strict Spiral** это правило не действует: retained Bézier/GPU rail остаётся точным authoritative carrier, и CPU/Canvas materialization не используется как тихая подмена.

### Источник истины для контура Web

Для обычной Static/Morph геометрии Web получает `FrameContour`. Он не должен повторно прогонять базовую форму через собственный rounded/morph builder. Его corner detection, clipping и placement работают относительно того же контура, который уже выбрала Line.

Для strict Spiral retained cubic/Arc ресурс остаётся специализированным authoritative carrier поздней 7.7.9. Это техническое исключение, а не отдельная форма Web.

### Что нельзя делать

- считать `showWeb === true` доказательством работы;
- иметь отдельную статическую форму нитей и другую Morph-форму нитей;
- позволять Base/Fill перетирать Web прозрачной полноэкранной композицией;
- открывать Web собственную независимую Layer Scene в обход `SomataLayerSceneService`.

## 18. Profile / Graffiti

Основные файлы:

- `js/render/profile-plan.js`

- `js/render/graffiti-pass.js`
- `js/gpu/graffiti-ribbon-renderer.js`

Profile определяет, как отображается основной carrier.

Graffiti — это не независимая фигура: он должен следовать той же актуальной геометрии.

Для обычной Static/Morph геометрии `profile-plan` и Graffiti получают тот же `FrameContour`, что Web и Lightning. ## 19. Lamps

Основные файлы:

- `js/render/lamp-plan.js`
- `js/render/lamp-pass.js`
- `js/render/lamp-morph-bridge.js`
- `js/gpu/lamp-renderer.js`
- `js/gpu/lamp-topology-resource.js`
- `js/gpu/lamp-ghost-resource.js`
- `js/geometry/lamp-corner-resource.js`

Lamps логически находятся после Base/Profile и до Lightning.

У разных Morph-режимов есть специализированные способы сохранить lamp identity, но главный compositor общается с **семантическим Lamp pass**, а не напрямую с каждым GPU renderer'ом.

Это позволяет менять внутренний способ отслеживания ламп без переписывания `main-pipeline.js`.

Для `Topology`/`Calm` Morph при включённом прилипании ламп действует canonical-инвариант, сохранённый из v505: topology lineage определяет identity лампы, но её **финальная позиция каждого кадра проецируется на текущий реально отображаемый rail**. Ускоренный resident topology resource не имеет права обходить эту последнюю проекцию, иначе лампа может интерполироваться между корректными source/target refs, но визуально отлипнуть от текущей линии. Если прилипание выключено, GPU topology shortcut снова разрешён. Strict Spiral сохраняет собственный exact Arc/retained carrier и этим правилом не заменяется.

Дополнительный контракт движения: финальная проекция не должна каждый кадр заново выбирать геометрически ближайший segment. На самопересечениях или близких ветвях это приводит к телепортации между разными местами одного spline. После определения stable lamp identity лампа хранит координату вдоль профиля (`pathIndex + arc fraction`). Если Topology transport уже публикует `lampAttachFraction`, именно она является непрерывной координатой движения; иначе nearest projection используется только как target и ограничивается предыдущей arc-позицией. Фактическая координата каждого кадра получается только выборкой точки на текущем `FrameContour` по этой arc-coordinate. Прямолинейный XY-handoff для уже привязанной к profile rail лампы запрещён.

Режим положения **«На изломах» является эксклюзивным**: он выводит только corner/bend lamps. Ключевые лампы принадлежат режиму «Ключевое» и не добавляются поверх изломов. Это возвращает проверенную семантику v505 и исключает две лампы в одной точке.

`Инерция излома` действует только во время Morph. Новая corner-lamp начинается с нулевого уровня и за заданное время линейно достигает полной яркости `1.0`; исчезающий излом за то же время уходит к нулю. В Static обнаруженный излом имеет уровень `1.0` сразу и не использует временную инерцию.

## 20. Sweep, Glint и Lightning

Основные файлы:

- `js/render/sweep-plan.js`
- `js/render/sweep-pass.js`
- `js/render/profile-sweep-adapter.js`
- `js/gpu/canonical-sweep-renderer.js`
- `js/gpu/bezier-sweep-renderer.js`
- `js/gpu/lightning-arc-renderer.js`

Sweep — общий класс проходящих по контуру эффектов. Lightning является одним из его режимов.

### Обычная Lightning

Текущий контракт 7.8.1:

```text
Static / Morph
      ↓
один FrameContour текущего кадра
      ↓
prepareLayerFrameSweepData()
      ↓
Lightning pieces / sampling
      ↓
SweepGPURenderer
```

Lightning имеет право добавлять jitter, ветвление, strike/precharge и менять sampling для своей визуальной природы. Она **не имеет права строить другую базовую линию**. Поэтому центр разряда, Graffiti и Line начинаются с одного carrier.

Статика и обычный Morph не переключаются между двумя несовместимыми Lightning backend'ами.

### Strict Spiral Lightning

Strict Spiral может использовать retained GPU Arc напрямую, потому что материализация обычного CPU Morph path разрушила бы точную специализированную геометрию.

Это техническое исключение должно быть локализовано в geometry/backend adapter, а не превращаться в другую художественную логику Lightning.

### Производительность Lightning

Особенно дорогими могут стать:

- слишком большое число logical segments;
- слишком большое `exactBezierRasterSubdiv`;
- повторная подготовка Arc на каждом кадре;
- перестройка bundles/bind groups вместо reuse;
- driver submission / presentation stalls.

Именно поэтому анализ нагрузки должен смотреть не только на FPS, но и на подготовку, encode, количество сегментов и фактический render/paint time.

### Почему единый FrameContour быстрее

До унификации несколько эффектов могли независимо получать текущую Morph-геометрию, делать rounding/resampling, строить таблицы длины и создавать временные массивы. Это не только давало разные визуальные контуры, но и повторяло одну и ту же CPU-работу в одном кадре.

Теперь для обычной геометрии дорогая часть выбора базовой формы делается один раз. `SomataFrameContourService` хранит результат на `frameCtx`; последующие потребители получают cache hit. Каждый эффект считает только то, что уникально именно для него: Web — нити, Graffiti — ribbon, Lightning — strike pieces.

Это не означает «один GPU pass на всё». Pass'ы остаются раздельными ради композиции и fault isolation. Общим стал **геометрический источник**, а не весь renderer.

## 21. Path FX: Moving Line и Sprite

Основные файлы:

- `js/render/path-fx-plan.js`
- `js/render/path-fx-pass.js`
- `js/gpu/path-fx-renderer.js`

Эти эффекты могут в некоторых режимах заменять обычный Base stroke.

Решение «заменён ли Base» принимается через общий контракт, а не через прямую зависимость Base от конкретной реализации Path FX.

Очереди видимых копий собираются по слоям и могут flush'иться один раз за основной кадр.

## 22. Particles

Основные файлы:

- `js/render/particle-pass.js`
- `js/gpu/particle-renderer.js`

Particles находятся наверху стеков эффектов.

Они используют GPU instancing и, где возможно, текущий resident Layer Scene.

Для динамической геометрии particles должны потреблять актуальный carrier/Arc, а не создавать вторую независимую форму.

## 23. Corridor

Corridor не является отдельной копией renderer'а. Он создаёт набор экземпляров/копий текущего слоя.

Правильная модель:

```text
одна актуальная геометрия слоя
        ↓
набор copy transforms / alpha / phase
        ↓
те же эффекты рисуют эти экземпляры
```

То есть Corridor не должен иметь «свою Web», «свою Lightning» и «свой Fill» с другой геометрической математикой.

### Center reveal

Скрытие центра является per-copy логикой. Нельзя после всех glow/effect проходов накрывать центр финальной маской, которая уничтожит уже корректно рассчитанный glow.

---

## 24. Master

Файл: `js/ui/master-broadcast-core.js` плюс UI-обвязка в runtime.

Master — это **broadcast изменений**, а не режим «сделать все слои одинаковыми».

Правильное поведение:

1. включение Master само по себе ничего не нормализует;
2. пользователь меняет параметр активного слоя;
3. система определяет, **какие конкретно property paths изменились**;
4. только эти пути копируются остальным слоям.

Renderer не должен содержать Master-логику.

---

## 25. Effect planning

Файл: `js/render/effects-plan.js`.

Центральный planner не содержит список `if web`, `if lightning`, `if particles`.

Каждый feature публикует capability для:

- сброса своего plan;
- подготовки своего plan;
- требований RenderGraph;
- admission в Layer Scene;
- lifecycle hooks.

Благодаря этому новый эффект должен подключаться через регистрацию, а не через разрастание центрального файла.

## 26. Изоляция ошибок pass'ов

Файл: `js/render/pass-isolation.js`.

Если Web, Lightning или другой отдельный pass падает:

1. ошибка записывается;
2. этот pass пропускается для текущего кадра;
3. scheduler остаётся жив;
4. следующий кадр может повторить попытку.

Один эффект **не имеет права убить весь render loop**.

В Full-GPU/strict случаях Canvas fallback не используется как тихая подмена.

## 27. GPU lifecycle

GPU renderer может находиться в состояниях:

```text
не запускался
→ initializing / warming
→ ready
→ временно недоступен
→ lost / failed
```

`initializing` — не ошибка кадра сама по себе.

Нормальная реакция:

- запросить warmup;
- запросить repaint;
- не замораживать общий scheduler;
- после устойчивого отказа выдать диагностируемую ошибку.

При `device lost` состояние GPU-ресурсов должно быть создано заново для новой generation.

## 28. Диагностика ошибок

Основной сервис: `js/render/render-diagnostics.js`.

GPU-ошибка получает стабильный fingerprint вида:

```text
GPU-XXXXXXXX
```

В payload должны быть:

- feature;
- stage;
- reason;
- frameId;
- layerId/layerIndex;
- активные Morph/Corridor режимы;
- активные эффекты;
- выбранный fallback;
- удалось ли восстановиться.

Смысл: сообщение должно отвечать не «что-то не нарисовалось», а **какой pass, на каком этапе, с какой причиной**.

## 29. FPS-консоль

Файл: `js/bootstrap/error-overlay.js`.

FPS-консоль имеет две задачи.

### Вкладка «Ошибки»

Она должна показывать, в частности:

- `console.error`;
- `window.error`;
- `unhandledrejection`;
- WebGPU `uncapturederror`;
- `device lost`;
- структурированные Somata GPU errors;
- Morph Freeze diagnostics.

Переключение на другую вкладку не должно уничтожать историю ошибок.

### Вкладка «Нагрузка»

При включённом анализе она показывает, что именно ест кадр прямо сейчас:

- FPS;
- frame budget;
- render/paint;
- scheduler task;
- CPU render passes;
- доступные GPU timings;
- hottest renderer counters;
- отдельные Lightning counters, когда Lightning активна.

Главный принцип этой вкладки: **не гадать по названию эффекта, а показывать измеренный bottleneck**.

## 30. Почему `paint` и CPU pass — не одно и то же

Это важно для расследования лагов.

Например, Somata может измерить:

```text
CPU prepare: 10 ms
JS render function: 20 ms
общий paint/renderMainCanvas: 300 ms
```

Это не противоречие.

Оставшееся время может уходить в:

- GPU command submission;
- driver synchronization;
- texture allocation;
- shader/pipeline compilation;
- WebGPU implementation;
- browser compositor/present.

Поэтому нельзя автоматически обвинять Morph, если Morph-task занял 1 ms, а весь `renderMainCanvas` занял 300 ms.

## 35. Как добавлять или менять эффект

Правильная последовательность:

1. Определить, **какую текущую геометрию** эффект должен видеть.
2. Описать его `FeatureHost` contract.
3. Описать его требования в RenderGraph.
4. Сделать plan — подготовить только данные, а не рисовать.
5. Сделать pass — выполнить rendering.
6. Если нужен Layer Scene — пользоваться `SomataLayerSceneService`.
7. Если нужен Exact Arc/другой prerequisite — зарегистрировать его через GPU scheduler/geometry capability, а не вычислять скрытую копию внутри pass'а.
8. Ошибку локализовать в pass и отправлять в общую диагностику.
9. Добавить regression-тест реального UI/renderer path.
10. Проверить эффект и в статике, и во время Morph.

## 36. Как НЕ надо чинить баги

### Не надо копировать код из 7.5 целиком

7.5 — хороший визуальный и поведенческий эталон для ряда эффектов, но поздняя 7.7.9 содержит более новую архитектуру Spiral, carrier mapping, firewalls и GPU scene routing.

Правильный подход:

> взять из 7.5 нужный **визуальный/математический контракт**, но встроить его в текущую архитектуру 7.8.3.

### Не надо добавлять ещё один fallback без понимания причины

Если Web исчез, сначала надо понять:

- Web не подготовился?
- Web не encoded?
- command не поставлен в очередь?
- Base затёр Web?
- Layer Scene не materialized?
- final present не произошёл?

И только потом менять код.

### Не надо чинить один эффект изменением геометрии всех эффектов

Если сломана Lightning, нельзя без необходимости менять Spiral transport или Morph semantics.

## 39. Самые важные правила проекта в десяти строках

1. **Один кадр — одна актуальная геометрия слоя.**
2. **Статика и Morph не должны иметь две художественные реализации одного эффекта.**
3. **Spiral transport не переписывает глобальный Morph mode.**

8. **Падение одного pass'а не убивает scheduler.**
9. **Любой новый баг сначала превращается в regression-тест.**
10. **Реальный GPU-результат важнее красивого “PASS” в тестовой оболочке.**

## 7.8.3: как Web действительно совпадает с Line и Fill

В 7.8.1 оставалась архитектурная лазейка. Для обычной фигуры `FrameContour` уже существовал, но Web мог использовать заново построенный «точный Bézier rail», а Corridor вообще считался отдельным исключением. На практике это означало: Line рисуется по одному master carrier, Fill — по другому подготовленному mesh, Web — по третьему rail. На сложной форме они расходились.

В 7.8.3 правило стало жёстким. Для обычной геометрии, включая обычный Corridor, существует **один master Line carrier** текущего кадра.

```text
обычная Static / Morph geometry
              ↓
      master Line commands
              ↓
         FrameContour
      ┌───────┼────────┐
      ↓       ↓        ↓
     Line    Fill      Web
```

Внутри `FrameContour` есть разные представления одной формы:

- `commands` — тот самый объект команд, который использует Line;
- `screenPaths` — эти же команды, соединённые в замкнутые/открытые контуры для Fill;
- `paths` / `visualLinePaths` — тот же видимый Line carrier в локальных координатах для Web;
- `anchorPaths` — только смысловые вершины для поиска углов Web.

`anchorPaths` **не являются визуальным контуром паутины**. Они только говорят: «вот здесь находится смысловой угол». После этого каждый найденный угол проектируется на ближайший `visualLinePaths`, и все расстояния, clipping и оба конца каждой нити вычисляются уже только по фактической линии. Поэтому разбиение `anchorPaths` и Line на разное число subpath'ов больше не ломает индексирование: Web не доверяет `pathIndex` authored-геометрии, а находит реальный Line path по ближайшей проекции.

Для обычного Corridor действует то же правило. Corridor — это не новая форма, а несколько transform-копий одного master contour. Поэтому 7.8.3 строит `FrameContour` прямо из **того же объекта Corridor master stroke commands**, который позже получает Base. Fill строит master mesh из этого FrameContour, Web строит master threads из него же, а затем Fill/Web/Line получают одинаковые Corridor transforms. Статический и Morph Corridor работают по одному принципу.

```text
Corridor master Line commands
          ↓
     FrameContour
    ┌─────┼──────┐
    ↓     ↓      ↓
   Fill   Web    Line
    └─────┴──────┘
          ↓
 те же copy transforms
```

Для Corridor композиционный порядок также физический и берётся из того же `SomataEffectStackOrder`; master Fill/Web/Line получают одинаковые copy transforms, а меняется только compositor phase их семантической группы. В заводском порядке это **Fill → Web → Geometry**. Если обязательный ordered Fill временно не готов, нельзя тихо дорисовать его позже в позиции, противоречащей текущему стеку; кадр перепрашивается. При этом Web не должен навсегда ждать успешного Fill и исчезать.

Отдельное исключение — strict Spiral. Его поздний retained GPU/Bézier carrier не заменяется generic FrameContour, потому что эта механика уже была правильной в поздней 7.7.9. Для него Web продолжает потреблять специализированный видимый rail.

Для Corridor Web также сохраняется GPU lifetime-инвариант: buffer, на который уже сослался deferred command buffer, нельзя уничтожать до `queue.submit`. При росте ring-buffer старая allocation уходит в retired-list и уничтожается только при teardown/reset renderer.

## 7.8.3: почему Web раньше «то работал, то нет» в статике

У режима Web есть разные способы выбора мест, где строятся нити. Режим `selfIntersection` по определению ничего не рисует на простой статической фигуре без самопересечений. Во время Morph такая же фигура может временно пересечь сама себя — и Web внезапно появляется. Визуально это выглядело как случайная поломка, хотя причиной был не GPU, а выбранный режим поиска опорных точек.

Начиная с 7.8.3 заводской режим Web — **«Паутина в углах» (`corners`)**, а **«Глубина в угол» — 60%**. Эти значения заданы одинаково в HTML, `state.web`, `DEFAULT_WEB_CONFIG`, UI fallback и GPU Morph bridge. В комплектном `default.plist` они также применены ко всем слоям, где Web был выключен; проекты, где Web уже был намеренно включён и настроен, не переписываются.

Static и Morph используют один `FrameContour`. Для режима `corners` статическая фигура обязана дать непустой набор углов и реальные Web thread commands уже на первом кадре после пользовательского включения. При Morph сохранён шаблон смысловых углов: если на промежуточном сглаженном кадре локальный детектор на мгновение не видит угол, Web не исчезает, а продолжает следовать тому же Line carrier.

Отдельно важно: загрузка `default.plist` выполняется без HTTP-кэша, чтобы при переходе на новую версию старые заводские настройки Web не подменяли новые дефолты из кэша браузера.


### Live-состояние Web во время Morph

Есть ещё один принцип, который в 7.8.3 сделан обязательным: **эффекты читают authored/live слой, а не Morph display-snapshot**. Morph имеет право создавать временную копию слоя для геометрии текущего кадра, но эта копия не является владельцем `showWeb`, Web config и остальных live-настроек эффектов.

Раньше `ensureLayerEffectState()` мог через runtime lookup найти именно Morph display-layer. Из-за этого реальный UI уже ставил `showWeb=true` в `state.layers`, а Web-plan в том же кадре видел старую snapshot-копию с `showWeb=false`. При следующем переключении мог происходить зеркальный эффект. Визуально это и выглядело как «паутина то работает, то нет».

Теперь поиск persistent effect owner всегда сначала идёт в authored `state.layers` по `id`, и только если такого слоя действительно нет — допускается runtime/display fallback. Поэтому ON/OFF Web во время активного Morph применяется на ближайшем кадре к тому же владельцу, который редактирует UI.


## 7.8.3: Topology Morph — Lamps и Particles обязаны следовать фактическому Profile rail

В Topology/Calm Morph нельзя считать endpoint-interpolated Morph Arc окончательной визуальной траекторией эффектов. Она может сохранять корректную topology identity, но расходиться с профилем, который реально рисует Line.

Для обычной, не strict-Spiral геометрии действует правило:

```text
Topology / Calm identity / transport
              ↓
      current FrameContour.paths
          ┌────────┴────────┐
          ↓                 ↓
       Lamps            Particles
   final projection     path table
```

`v505` остаётся эталоном семантики Lamp identity: сначала определяется соответствие лампы в Topology Morph. Но окончательная координата при включённом прилипании обязана проецироваться на `FrameContour.paths` текущего кадра — тот же carrier, который реально использует обычная Line.
При этом проекция является **arc-stable**, а не независимым nearest-point solve на каждом кадре: stable identity переживает смену topology slot'ов между Morph-циклами, а `profile-arc` состояние переживает эту смену вместе с identity. Поэтому близкие ветви spline не могут перехватить лампу только потому, что на одном кадре оказались на несколько пикселей ближе.

Particles в Topology/Calm также не должны брать generic GPU Morph Arc как визуальный rail. Для них строится typed path table непосредственно из текущего `FrameContour.paths`. Благодаря этому Lamps и Particles следуют тому же пользовательскому Shape Profile, включая spline/rounding текущего кадра.

Это правило относится именно к ordinary Topology/Calm. **Strict Spiral не переводится на FrameContour**: её authoritative carrier остаётся retained exact Bézier/GPU Arc.

## 7.9 — стабильный baseline и первая performance-итерация Fade

Версия **7.9** считается новым стабильным baseline после исправлений Fill/Web, MSAA accumulation, configurable effect order, topology attachment Lamps/Particles, lamp spline motion/corner inertia и Fade Hardness.

### Continuous Fade field

`Затухающая — плавная` больше не строит глубину из 8 направлений × 3 дискретных радиуса. В 7.9 это отдельная optional GPU materialization:

```text
current-frame isolated Fill texture
        ↓
1/2-resolution horizontal Gaussian field
        ↓
1/2-resolution vertical Gaussian field
        ↓
continuous contour-depth texture
        ↓
Fade composite
```

Это техническая materialization Fill, а не новая геометрия. `FrameContour`, Fill topology, Web и остальные эффекты не знают о blur field.

Контракты:

- базовые `Плотный`, `Математический`, `С накоплением` не зависят от continuous Fade pipeline;
- отказ advanced Fade shader/pipeline не имеет права переводить базовый Fill renderer в failed;
- continuous resources создаются **лениво**, только когда активен `fadeSmooth` или пользователь повышает детализацию sharp Fade выше baseline;
- field строится в **1/2 разрешения** и линейно семплируется при composite; это уменьшает texture-sample нагрузку относительно прежних 24 full-resolution directional samples;
- `Жёсткость` по-прежнему только монотонно двигает порог: `0% = пусто`, `100% = полная Fill`.

### Пикселизация sharp Fade

У `Затухающая — резкая` есть `fillFadePixelization`:

```text
0%   → более крупные ступени
25%  → сохранённый визуальный baseline 7.9
100% → continuous field / плавный градиент
```

При `<=25%` sharp Fade остаётся на дешёвом legacy binary-ring path. Continuous field не материализуется. При `>25%` sharp-field постепенно смешивается с continuous field. Поэтому обычный baseline не платит за качество, которое пользователь не запросил.

### Performance-правило следующих итераций

7.9 закрепляет общий принцип дальнейшей оптимизации:

> **Оптимизировать не эффект целиком, а materialization/demand. Дорогой representation создаётся только когда активный consumer действительно его запросил. Базовые carriers и эффекты не должны переходить на универсальный дорогой путь “на всякий случай”.**

Следующие безопасные итерации после визуальной проверки 7.9:

1. отделить логическую identity кадра от переиспользуемого `frameCtx` и вынести transient outputs в frame-owned generation;
2. формализовать общий `GeometryCarrier` capability contract перед будущими Dreamcatcher/Tesseract;
3. добавить frame trace DAG для prepare/encode/submit/present и использовать его для точечного удаления redundant materializations;
4. объединять только совместимые GPU sections внутри одного encoder, сохраняя независимый художественный порядок Fill/Web/Geometry;
5. перейти к единому `FrameClock/VisualClock` без локальных time sources.

## 7.11.0 — два представления интерфейса: Pro и Easy

7.10.9 остаётся стабильной художественной базой. Начиная с 7.11.0 интерфейс имеет два режима представления одних и тех же данных:

- **Pro** — текущая плотная рабочая компоновка без упрощения функций.
- **Easy** — более читаемое представление того же состояния и тех же renderer/Morph/Audio contracts.

Переключение Easy/Pro является только UI preference и не входит в authored project state. Оно не имеет права менять слои, параметры, Morph Profiles, Audio routes, Orange generation, renderer или scheduler.

Easy использует progressive disclosure: основные параметры остаются на виду, технические коэффициенты и точные служебные настройки доступны через «Дополнительно». Если дополнительный параметр уже отличается от исходного значения, Easy не скрывает его молча. Левый tool rail получает текстовые названия разделов, а routable-параметры получают discoverability-подсказку о ПКМ-связях Blue / Orange / Audio.

Blue, Orange и Audio продолжают пользоваться одним shared Parameter Registry и одинаковыми группами. Orange 7.11.0 получает тот же routing-подход, adaptive brightness для создаваемых Lamp-композиций и не останавливается от ручной правки параметра или повторной генерации «костью»; ручные включения/выключения внутри активного типа Morph сохраняются как пользовательское решение до следующего явного изменения.
